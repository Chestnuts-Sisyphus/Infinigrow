# 版本体系：v1 与 v2 的关系

## 两代是什么

| 代 | 代号 | 状态 | 说明 |
|---|---|---|---|
| v1 | `Cultivar` | **封存**（不再开发） | 长期演化的运行体：单体源文件、内嵌夹具、宿主目录下的状态根、历史机制词叠加 |
| v2 | `Infinigrow` | **当前线** | 只保留机制本身的重写：判据清晰、状态可搬、路径零硬编码 |

**v2 不是 v1 的升级版，是断代重写。** 这一点是刻意的：

v1 的问题不是某几个 bug，而是**同一条规则在两处写、两边各自演化**——
提示词里留着「完成即分岔必须自造新芽」的旧条款，设计与代码里写的是「芽＝预测差异的产物」。
两条规则并存的结果是：执行会话每拍自造一根复述芽，队列里 221 根待长有 186 根同族、
题面逐字相同，引擎原地打转。在这样一个「新旧叠加」的载体上继续打补丁，
每个补丁都会先与残留条款打架。

所以 v2 的建立方式是：**从机制重新写一遍**，并把「防止再次叠加」做成机器能查的规则
（见 `infinigrow scan`，其中 R3 专门盯旧条款回归）。

## 版本号规则

- **主版本**（`x.0.0`）：判据层变化——边/成熟链/差异类型/芽源的语义变更，或**不兼容的**账本格式
  变更（同一份账本在新旧代码下读出不同判决，或旧代码读新行直接失败）。
  改这里＝改公设，必须同时更新 `docs/zh/mechanism.md` 与提示词（同源校验会拦住只改一处）。
- **次版本**（`2.x.0`）：新增能力但判据不变（例如新加一条规则、新加一个记账视图）。
- **修订号**（`2.0.x`）：修缺陷、改文档、改测试，以及**兼容的**账本格式变化——掉一个键、加一个
  可空键，只要旧行照读、缺键读作 `None`、多余键忽略，就还算修订号，不是主版本。
  先例：S9 删掉 `long_task` 的序列化键按 `2.2.27` 发布（拍 647 实测：4,370 行账本全带该键、
  **0 行为 true**，`Sprout.from_record` 忽略多余键，旧账本一字不动仍可被新代码读）——
  它没改任何判决，所以不是主版本。判据落在读侧：`as_record()` 不写退役键、`from_record` 容忍残留。

v2 从 `2.0.0` 起算，**不发布 `1.x` 的后续版本**（v1 线在封存那一刻停止）。
版本号的单一事实源是 `src/infinigrow/__init__.py` 的 `__version__` 与
`pyproject.toml` 的 `version`；两者不一致会被 `tests/test_version.py` 拦下。

## 代号

`Infinigrow` ＝ infini（无限）＋ grow（生长）：**生长本身就是那个无限的东西**，
不是「在无限空间里生长」。旧代号 `Cultivar` 保留在本文件里作为历史称呼。
